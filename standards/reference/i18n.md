# Internationalization Principles

Library-agnostic. For the concrete API (`t()`, `$t`, a pipe, a directive) see the
`framework/*.md` file for your stack.

## Non-negotiables

- **No hardcoded user-facing strings.** Every string a user can read goes through
  the translation layer — including `aria-label`, `placeholder`, `title`, `alt`,
  toast and alert copy, validation messages, and empty-state text
- Support every required locale from the first commit. Retrofitting i18n costs
  far more than doing it inline
- A missing key must be visible in development, never silently rendered as an
  empty string

## Keys

- lowerCamelCase, dot-separated, grouped by feature: `profile.saveButton`
- Name keys for **meaning**, not for the English text. `t('form.submitButton')`,
  never `t('Submit')` — using the source string as the key breaks the moment the
  copy changes and makes the default locale load-bearing
- Do not build keys by string concatenation at runtime; static analysis and
  unused-key tooling cannot follow them. Use an explicit lookup map instead

## Formatting

- Use the `Intl` API for dates, numbers, currency, plurals, relative time, and
  list joining. Never hardcode a locale-specific format or assemble one by
  concatenation
- Never concatenate translated fragments into a sentence — word order differs
  between languages. Use interpolation within a single key:
  `t('cart.itemCount', { count })`
- Pluralization goes through the library's plural support, not an `if`. Several
  languages have more than two plural forms

## Content that is not translatable

Do not route these through the translation layer:

- Console messages and developer-facing errors
- URLs, API paths, and route segments
- Enum values, type literals, and analytics event names
- Code comments

## Review checks

- New keys added to **all** locale files, not only the default
- Unknown translations marked with an explicit `TODO: translate` placeholder so
  they are greppable — never left absent
- No string literal reaching a user-visible slot
